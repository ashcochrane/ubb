# Reviewed contract breaks, ERR level — cumulative since `api-v1-launch`.
#
# The gate (`python openapi/contract_gate.py`, run by CI) compares the spec at
# the immutable `api-v1-launch` tag against the working tree. So this file
# answers one question: has every break since the contract was published been
# reviewed? Each entry below is one break that has.
#
# THREE RULES — the reasoning behind each is in openapi/README.md:
#
#  1. Entries are GENERATED, never hand-typed:
#         python openapi/contract_gate.py --baseline origin/main --emit
#     Hand-derivation once put seven WARN-level lines in this file, where
#     `--err-ignore` silently did nothing for them, and missed two ERR findings
#     entirely. An entry that suppresses nothing now turns the gate red.
#  2. ERR-level findings ONLY — WARN-level ones live in the sibling
#     oasdiff-warn-ignore.txt. The two flags filter by level before matching
#     text, so a line in the wrong file is a no-op, not a near-miss.
#  3. Human metadata belongs on `#` comment lines: slice, date, pull request,
#     decision references, and why the break is accepted. A non-comment line
#     that is not a generated finding matches nothing, and the gate says so.
#
# THIS FILE CANNOT REACH ZERO while the baseline is `api-v1-launch`. The
# differences from that tag are real and intentional, and they accumulate as
# each slice lands. It clears only when slice 8 tags a NEW baseline and the gate
# is pointed at it (migration/cutover decision §7.5); `api-v1-launch` itself is
# never moved or deleted. This is a DIFFERENT MECHANISM from the
# implementation-rule migration ledgers, which are seeded with today's known
# violations and must shrink to empty by slice 8. Growing-and-intentional vs
# shrinking-and-defective — do not conflate them.
#
# So never delete an entry to make this file shorter. Delete one only when the
# gate reports it INERT, which means it no longer describes a real break and has
# become a lie; regenerate rather than edit it by hand.
#
# WHAT MAY BE ADDED. Because the baseline *is* the launch tag, every entry here
# is by construction a post-launch break; the pre-launch lane that the old
# `LAUNCH TAG BOUNDARY` marker separated cannot appear in this comparison at
# all, so the marker is gone. Its 20 pre-tag entries (#78, #86) went with it:
# the tag already contains those changes, so they matched nothing and the gate
# reported them inert. They remain in git history (see #195, which installed the
# cumulative comparison). A NEW entry is permitted only:
#   - in the PRE-LIVE LANE — no tenant is integrated against v1, so the break is
#     hand-coordinated with the one known consumer. docs/api-compatibility.md
#     carries the dated note and names the day it is deleted; the re-model's
#     licence is #137 constraint 1, reaffirmed by migration/cutover §7.1; or
#   - as evidence of an ADR-003 §4 DEPRECATION already in flight: `deprecated:
#     true` on the operation, a runtime `Sunset` header (register the route in
#     api/v1/deprecation.py), a dated changelog entry + email announcement, and
#     at least 90 days' notice (a floor we may raise, never lower).
# From the first live tenant, only the second remains. A bare removal or rename
# is a contract breach, not a CI escape hatch. See docs/api-compatibility.md.

# "list-of-types widened by adding `null`". Recording one and not the other
# would leave the gate red on a break already reviewed, so both lines sit here
# under one reason.
#
# WHY THE FIELD MOVED. `Posting.billed_cost_micros` is nullable as of this
# commit, with `pricing_status` beside it saying which of four readings a NULL
# takes. Before it, "we priced this at nothing" and "we could not price this"
# were the same row: a customer who should have been charged and was not looked
# exactly like one correctly charged nothing. A response that could not
# serialise the absent case would have been a document contradicting its own
# server the moment the resolver started writing it.
#
# ⚠ ONLY THE DETAIL RESPONSE IS A BREAK, AND THAT IS WORTH SAYING. The other
# two responses carrying this amount — the recording ack and the list row —
# have been `Optional` since long before this slice, while the COLUMN behind
# them was NOT NULL with a default of zero. Their nullability was decorative:
# no posting could produce a null to put through it. So this slice made the
# absent case REACHABLE on all three and EXPRESSIBLE on only one. The exact
# asymmetry #320 recorded for the supplier half, on the other amount.
#
# NOTHING WAS REMOVED AND NOTHING RENAMED. The property keeps its name, its
# type and its position; what changed is that `null` joined the type list. The
# two fields added beside it (`pricing_status`, `not_applicable_reason`) are
# additive and are not breaks.
#
# WHY THE PRE-LIVE LANE APPLIES: no tenant is integrated against v1 (ADR-0007

# layer was widened with it, so an unresolved price renders as an absence

# --- slice 5 (#409): the unit-of-work lifecycle moves to the root prefix -----
#
# Reading one unit of work, listing them and closing one leave `/metering/` for
# the root prefix, ungated:
#
#     GET  /api/v1/metering/tasks             -> GET  /api/v1/tasks
#     GET  /api/v1/metering/tasks/{task_id}   -> GET  /api/v1/tasks/{task_id}
#     POST /api/v1/metering/tasks/{id}/close  -> POST /api/v1/tasks/{id}/close
#
# A unit of work is a KERNEL concept: metering hangs postings off it, billing
# starts one behind its spend gate and will key a charge on how it ended, and
# spend control kills one. A thing several products realize and none owns is
# mounted at the root prefix — the rule `/plans` and `/event-types` already
# follow, and which `api/v1/event_type_endpoints.py` names these very routes as
# NOT having settled: they sat under `/metering/` *because they predate that
# rule, not because it spared them*. ADR-0007 §3 forbids breaking a name twice
# to repair a first break, so leaving them there would have made the mismatch
# permanent.
#
# ⚠ ONLY ONE OF THE THREE REMOVALS APPEARS BELOW, AND THAT IS THE CUMULATIVE
# COMPARISON WORKING RATHER THAN TWO LINES SOMEBODY FORGOT. The two reads did
# not exist at the `api-v1-launch` tag — they arrived after it and depart here,
# so a diff against the tag sees neither their arrival nor their departure and
# emits nothing for either. This is the shape #368 and #369 both recorded, and
# it is why BOTH directions were run: the authoring direction (`--baseline
# origin/main`) reports all three, the cumulative gate reports one, and only
# what the cumulative gate is missing may be filed. Pasting the other two would
# fail this gate as suppressions that suppress nothing.
#
# ⚠ THE CLOSE'S NEW REQUIRED `outcome` EMITS NOTHING EITHER, for the reason the
# deleted component schemas above emit nothing: the body arrives on a path
# `oasdiff` sees as ADDED, so there is no before-and-after body to compare. The
# requirement is real, and it is the sharpest part of this change — a close now
# refuses to default to a delivery, because the forgiving path must never be
# the money-moving one — but it is not a break the tool can report, and a
# hand-typed line for it would suppress nothing.
#
# WHY THE PRE-LIVE LANE APPLIES: no tenant is integrated against v1 (ADR-0007
# §5 — the launch tag is not what binds), and every known consumer moves in
# this same commit — the SDK core, its hand-written `close_task`, the console's
# committed schema snapshot, and the platform's own tests.
POST /api/v1/metering/tasks/{task_id}/close api path removed without deprecation
